00 · Punto de partida

¿Por qué usar datos reales?

En muchos proyectos académicos de redes se crean grafos "de juguete" con nodos y aristas inventados. Este proyecto no hace eso. Queremos que el análisis tenga valor real: que Dijkstra y Floyd-Warshall den respuestas sobre un ataque que realmente ocurrió.

Pregunta de investigación

En la campaña SolarWinds Compromise (2019–2020), ¿cuál es la secuencia de técnicas de ataque de menor resistencia desde el acceso inicial hasta el impacto, y qué técnicas representan cuellos de botella críticos según Dijkstra y Floyd-Warshall?

Para responder esto necesitamos:

  1. Un ataque documentado → SolarWinds Compromise
  2. Las técnicas que usaron → Base de datos MITRE ATT&CK
  3. Pesos reales → Mitigaciones + CVEs del NIST/NVD
  4. Un grafo modelado → DiGraph con Dijkstra y Floyd-Warshall
01 · El caso de estudio

¿Qué fue SolarWinds?

En 2019–2020, un grupo de atacantes (atribuido a APT29 / Cozy Bear, vinculado a Rusia) comprometió la cadena de suministro de software de SolarWinds, una empresa que vende herramientas de monitoreo de redes llamadas Orion.

🏭

Analogía: veneno en la fábrica

Imagina que en vez de atacar cada tienda individualmente, el atacante envenena directamente la fábrica donde se produce un producto. Orion era usado por ~18.000 organizaciones, incluyendo agencias del gobierno de EE.UU. Al comprometer la fábrica (el proceso de build de SolarWinds), todos los clientes que actualizaron el software recibieron automáticamente el malware SUNBURST.

¿Por qué es importante para este proyecto?

MITRE ATT&CK documentó exactamente qué técnicas usaron los atacantes durante toda la campaña. No es una estimación — es el resultado de investigación forense real publicada. Eso nos da:

71 técnicas documentadas 14 tácticas del kill chain CVEs reales con CVSS Mitigaciones por técnica
Fecha del ataque

El ataque ocurrió entre marzo 2019 y diciembre 2020. Fue descubierto por FireEye en diciembre 2020. Las víctimas incluyen Microsoft, Intel, Cisco, y múltiples agencias del gobierno de EE.UU. (Departamento del Tesoro, Seguridad Nacional, etc.).

02 · La fuente de datos

MITRE ATT&CK — el dataset

📚

¿Qué es MITRE ATT&CK?

MITRE es una organización sin fines de lucro de EE.UU. que trabaja con el gobierno. ATT&CK (Adversarial Tactics, Techniques & Common Knowledge) es una base de conocimiento pública que documenta cómo los ciberatacantes reales operan en el mundo real.

No es una base de datos teórica — cada técnica en ATT&CK fue observada en ataques reales. MITRE la actualiza continuamente basándose en reportes de incidentes, inteligencia de amenazas y análisis forense.

Estructura de ATT&CK

Nivel 1

Tácticas

El objetivo del atacante. ¿Qué quiere lograr ahora? Ej: "Initial Access" = entrar al sistema.

Nivel 2

Técnicas

El cómo logra ese objetivo. Ej: "Phishing" para obtener acceso inicial.

Nivel 3

Sub-técnicas

Variantes específicas. Ej: T1566.001 = Spearphishing con adjunto.

Lo que descargamos

El archivo enterprise-attack.json del repositorio oficial de MITRE en GitHub. Pesa ~35 MB y contiene 25.842 objetos STIX: todas las técnicas, campañas, grupos de actores, mitigaciones y relaciones documentadas hasta la fecha.

03 · El formato de los datos

STIX 2.1 — el idioma de la ciberseguridad

🗣️

Analogía: un idioma estándar

Así como hay estándares para intercambiar datos médicos (HL7) o financieros (ISO 20022), la industria de ciberseguridad usa STIX (Structured Threat Information eXpression) para intercambiar información sobre amenazas. Es JSON, pero con estructura y tipos definidos.

¿Cómo luce un objeto STIX?

Cada objeto en el bundle es un JSON con campos estándar. Por ejemplo, una técnica ATT&CK es un objeto tipo attack-pattern:

{
  "type": "attack-pattern",
  "id": "attack-pattern--b17a1a56-e99c-403c-8948-561df1792c38",
  "name": "Valid Accounts",
  "external_references": [
    { "source_name": "mitre-attack", "external_id": "T1078" }
  ],
  "kill_chain_phases": [
    { "kill_chain_name": "mitre-attack", "phase_name": "initial-access" },
    { "kill_chain_name": "mitre-attack", "phase_name": "persistence" }
  ]
}

Tipos de objetos en el bundle

Tipo STIX¿Qué representa?Ejemplo

Por qué importa el tipo

El código Python filtra por type para extraer exactamente lo que necesita. Cuando buscamos las técnicas de SolarWinds, filtramos objetos tipo relationship donde relationship_type == "uses" y la fuente es la campaña SolarWinds.

04 · La descarga

El bundle descargado

El script Python descarga enterprise-attack.json y lo guarda localmente como caché. La próxima vez lo carga del disco sin descargar de nuevo.

# URL oficial del repositorio MITRE
MITRE_URL = "https://raw.githubusercontent.com/mitre/cti/master/"
            "enterprise-attack/enterprise-attack.json"

# Se guarda en data/mitre_attack.json (~35 MB)
def download_mitre(force=False) -> dict:
    if CACHE_PATH.exists() and not force:
        return json.load(open(CACHE_PATH))  # Usa caché local
    # Si no existe, descarga y guarda
    data = json.loads(urllib.request.urlopen(MITRE_URL).read())
    json.dump(data, open(CACHE_PATH, "w"))
    return data

¿Qué hay dentro?

El bundle es un diccionario con una clave "objects" que contiene una lista de ~25.000 objetos STIX:

{
  "type": "bundle",
  "id": "bundle--...",
  "objects": [
    { "type": "attack-pattern", ... },  # técnica
    { "type": "campaign", ... },        # campaña
    { "type": "relationship", ... },    # conexión
    # ... 25.839 objetos más
  ]
}

El código hace una sola pasada por todos los objetos para construir un índice id_map que permite acceder a cualquier objeto en O(1) por su ID STIX:

id_map = {o["id"]: o for o in bundle["objects"]}
# id_map["attack-pattern--b17..."] -> objeto completo de T1078
05 · La campaña

La campaña como objeto STIX

Una campaña en MITRE ATT&CK es un conjunto de actividades de ataque con un objetivo común, realizadas por uno o más actores. SolarWinds Compromise está documentada como:

{
  "type": "campaign",
  "id": "campaign--808d6b30-df4e-4341-8248-724da4bac650",
  "name": "SolarWinds Compromise",
  "created": "2021-05-19",
  "modified": "2023-09-12"
}

El código encuentra esta campaña buscando por nombre:

campaign = next(
    o for o in bundle["objects"]
    if o.get("type") == "campaign"
    and "SolarWinds" in o.get("name", "")
)
El ID STIX es la clave

Una vez encontrada la campaña, su id STIX se usa para buscar todas las relaciones donde la campaña "uses" técnicas. No usamos el nombre para buscar relaciones — usamos el ID porque es único y no cambia.

Las 71 técnicas de SolarWinds

Se extraen buscando relaciones uses donde el origen es la campaña y el destino es un attack-pattern. Solo se incluyen técnicas no revocadas y no deprecadas (ATT&CK actualiza y retira técnicas):

tech_ids = set()
for o in bundle["objects"]:
    if (o.get("type") == "relationship"
            and o.get("relationship_type") == "uses"
            and o.get("source_ref") == campaign["id"]       # La campaña la usó
            and o.get("target_ref", "").startswith("attack-pattern--")):
        tech_ids.add(o["target_ref"])  # Agrega el ID de la técnica

Resultado: 71 técnicas reales documentadas en la campaña SolarWinds. Algunas tienen IDs de tipo T1078 (técnica padre) y otras T1078.001 (sub-técnica).

07 · La estructura del grafo

Relaciones STIX — aristas del grafo

Las relaciones en STIX son objetos separados con un source_ref y un target_ref. Son el pegamento que conecta todos los objetos del bundle.

Tipos de relaciones usadas

relationship_typeSource → Target¿Qué significa?Uso en el proyecto

mitigates course-of-action → attack-pattern Esta medida defensiva contrarresta esta técnica Calcula el peso de cada nodo

¿Por qué no hay aristas directas "técnica → técnica" en STIX?

ATT&CK no documenta qué técnica lleva a qué otra — solo documenta qué técnicas usó cada campaña. La progresión táctica (las aristas del grafo) la inferimos nosotros a partir del orden del kill chain, conectando técnicas de tácticas consecutivas dentro de la misma campaña.

08 · El peso de las aristas

Mitigaciones como proxy de peso

El peso de cada arista representa qué tan costoso es para el atacante usar esa técnica. A más costo = más resistencia = camino menos atractivo para Dijkstra.

🛡️

Analogía: carreteras con peajes

Si hay muchas medidas de seguridad documentadas para una técnica, es una "carretera con muchos peajes" — cara para el atacante. Si hay pocas o ninguna mitigación, es una "autopista libre" — barata y peligrosa.

¿Qué es una mitigación en ATT&CK?

Una mitigación es un course-of-action (medida de seguridad) que MITRE documenta como efectivo contra una técnica específica. Ejemplos:

ID MitigaciónNombre¿Qué hace?
M1032Multi-factor AuthenticationRequiere un segundo factor para autenticarse
M1026Privileged Account ManagementLimita quién tiene cuentas privilegiadas
M1018User Account ManagementControla creación y permisos de cuentas
M1027Password PoliciesObliga contraseñas fuertes y rotación

La fórmula de peso

El número de mitigaciones se convierte en peso con esta fórmula:

# n_mitigaciones: cuántas mitigaciones tiene esta técnica en ATT&CK
# max_mitigaciones: máximo en la campaña SolarWinds (=8)
w = 1.0 - (n_mitigaciones / max_mitigaciones)

# Ejemplos:
# 0 mitigaciones → w = 1.0 - 0/8 = 1.0 → pero mínimo es 0.95
# 4 mitigaciones → w = 1.0 - 4/8 = 0.50
# 8 mitigaciones → w = 1.0 - 8/8 = 0.0 → pero mínimo es 0.05

w = max(0.05, w)  # nunca llega a cero (siempre hay algo de riesgo)

09 · Peso extra con CVEs

CVEs y CVSS — peso desde vulnerabilidades reales

🔓

¿Qué es un CVE?

CVE (Common Vulnerabilities and Exposures) es un identificador único para una vulnerabilidad específica. Lo gestiona MITRE y cada CVE está en la base de datos del NIST llamada NVD (National Vulnerability Database). Ejemplo: CVE-2020-10148 = vulnerabilidad crítica en SolarWinds Orion que permitió el ataque de supply chain.

¿Qué es CVSS?

CVSS (Common Vulnerability Scoring System) es una puntuación de 0 a 10 que indica qué tan grave es una vulnerabilidad:

Rango CVSSSeveridadInterpretación
0.1 – 3.9LowPoco peligrosa, difícil de explotar
4.0 – 6.9MediumModeradamente peligrosa
7.0 – 8.9HighMuy peligrosa
9.0 – 10.0CriticalExplotable remotamente, sin autenticación

Cómo se convierte CVSS en peso

# CVSS 9.8 (crítico) → peso muy bajo → fácil para el atacante
w_cve = (10.0 - cvss) / 10.0
# CVSS 9.8 → w = (10 - 9.8) / 10 = 0.02 → mínimo sube a 0.05
# CVSS 8.1 → w = (10 - 8.1) / 10 = 0.19
# CVSS 9.0 → w = (10 - 9.0) / 10 = 0.10

# Se toma el MÍNIMO entre peso por mitigaciones y peso por CVE
w_final = min(w_mit, w_cve)
# Peor escenario para el defensor = mejor escenario para el atacante

Cómo se construye el grafo

Nodos: 73 en total

71 nodos

Técnicas reales

Cada técnica documentada de SolarWinds. Con ID ATT&CK, táctica, peso calculado.

+1 nodo

ATTACKER

Nodo conceptual: el atacante externo antes de entrar. Peso = 0.

+1 nodo

IMPACT

Nodo conceptual: objetivo final logrado. Permite cerrar el grafo matemáticamente.

¿Por qué ATTACKER e IMPACT si no son técnicas reales?

Dijkstra necesita un nodo origen y un nodo destino. ATTACKER representa al adversario externo antes de usar cualquier técnica, e IMPACT representa el objetivo final. Sin ellos, no habría forma de formular la pregunta "¿cuál es la ruta más corta desde el inicio hasta el impacto?".

Aristas: 653 en total

Las aristas representan la progresión táctica del atacante dentro del kill chain. La lógica: si en SolarWinds usaron técnicas de táctica A y técnicas de táctica B, y B viene después de A en el kill chain, entonces desde cualquier técnica de A se puede ir a cualquier técnica de B.

# Para cada par de tácticas consecutivas [tac_i, tac_i+1]:
for src_id in tecnicas_de_tactica[tac_i]:
    for dst_id in tecnicas_de_tactica[tac_i+1]:
        G.add_edge(src_id, dst_id,
                   weight=peso_del_destino,  # el costo es llegar al destino
                   rel_type="tactical-progression")
Importante: el peso va en el destino, no en el origen

El peso de una arista A → B es el peso del nodo destino B. Esto refleja el costo que le cuesta al atacante ejecutar la técnica B (llegar al estado B), no el costo de salir de A.

11 · El kill chain

¿Por qué esta ruta y no otra?

Dijkstra eligió esta ruta porque su suma de pesos es la mínima posible. Nótese que T1078.003 (Local Accounts, w=0.50) y T1048.002 (Exfiltración, w=0.50) son los pasos más costosos. Las técnicas de discovery, staging y C2 tienen peso mínimo (0.05, sin mitigaciones), lo que hace esta ruta óptima.

Sección 14

Limitaciones del modelo

Todo modelo es una simplificación de la realidad. Reconocer explícitamente las limitaciones es requisito científico: permite al lector interpretar correctamente los resultados y saber cuándo el modelo puede no aplicar.

L1 · Aristas inferidas, no observadas

Las aristas del grafo conectan técnicas de tácticas consecutivas de la kill chain, pero no son secuencias de ataque directamente observadas en logs reales. Representan que el atacante podría haber transitado de táctica i a táctica i+1, no que lo hizo en ese orden exacto en cada intrusión documentada.

Implicación: el número de aristas (653) sobreestima las transiciones reales. Un modelo basado en datos de tráfico de red o SIEM reduciría esta incertidumbre.

L2 · El atacante no siempre elige el óptimo

Dijkstra asume que el atacante racional elige siempre el camino de menor resistencia. En la realidad, los actores de amenaza pueden elegir rutas subóptimas por preferencia de herramientas, falta de información, o para evadir detección (caminos más costosos pero más silenciosos).

Implicación: la ruta crítica es el peor escenario razonable para el defensor, no una predicción exacta del comportamiento del atacante.

L3 · ATT&CK es conocimiento histórico

El bundle MITRE ATT&CK Enterprise documenta técnicas ya observadas en campo. Técnicas nuevas o variantes no documentadas (zero-days, TTPs emergentes) no aparecen en el grafo. El modelo tiene un sesgo hacia amenazas conocidas.

Implicación: el análisis es válido para el threat model de SolarWinds (2019-2020). Un actor que use técnicas post-2023 podría encontrar rutas no modeladas.

L4 · Granularidad de los pesos

Con max_mitigaciones=8, la fórmula w = max(0.05, n_mit / 8) produce solo 9 valores posibles (0.05, 0.125, 0.25, 0.375, 0.5, 0.625, 0.75, 0.875, 1.0). Esto crea empates frecuentes (ej. múltiples técnicas de discovery con w=0.05), donde Dijkstra elige según orden de visita en el heap, no por una diferencia real de dificultad.

Implicación: rutas con costos idénticos son equivalentes. El análisis de sensibilidad (Jaccard=1.0 en ±20%, ruta cambia con esquema binario) confirma que la táctica crítica es robusta ante variaciones proporcionales.

L5 · Una sola campaña analizada

Los resultados son específicos de SolarWinds Compromise (2019-2020). No se puede afirmar que la metodología produce los mismos patrones en otras campañas sin haberlo verificado. T1606.001 puede no ser el nodo de mayor betweenness en un ataque de ransomware o en una campaña de espionaje diferente.

Implicación: la generalización del método requiere validación en múltiples campañas (APT28, FIN7, Lazarus Group). Es trabajo futuro documentado.

L6 · CVE-weights: asociación manual

La tabla KNOWN_CVE_WEIGHTS asigna CVEs a técnicas ATT&CK manualmente, basada en reportes públicos (CISA, FireEye, Microsoft). Esta asociación es una decisión del analista: otros investigadores podrían asignar CVEs diferentes a las mismas técnicas.

Implicación: el análisis de sensibilidad "sin CVE" (Jaccard=0.75) acota el efecto: con o sin CVE-weights, la ruta crítica cambia en 1 nodo de 7, y la táctica principal (credential-access) permanece.

Trabajo futuro sugerido

  • Comparar resultados en 3-5 campañas ATT&CK adicionales para verificar generalización
  • Reemplazar aristas inferidas por datos de co-ocurrencia de técnicas en incidentes reales (datasets VERIS, MITRE ATT&CK Evaluations)
  • Modelar comportamiento no-óptimo del atacante con cadenas de Markov o simulación Monte Carlo
  • Automatizar asignación CVE-técnica desde NVD API en lugar de tabla manual
  • Incorporar temporalidad: el grafo asume el ataque como estático; un modelo dinámico reflejaría mejor la evolución de la campaña

Glosario completo

ATT&CK
Adversarial Tactics, Techniques & Common Knowledge. Base de datos de MITRE con técnicas de ataque reales documentadas. Cada técnica tiene un ID tipo T1078.
STIX 2.1
Structured Threat Information eXpression. Formato JSON estándar para compartir información de ciberseguridad. El bundle de ATT&CK está en STIX 2.1.
Bundle STIX
El archivo JSON completo que contiene todos los objetos: técnicas, campañas, mitigaciones, relaciones. En este proyecto: enterprise-attack.json (~35 MB).
attack-pattern
Tipo de objeto STIX que representa una técnica de ataque. Cada técnica ATT&CK (T1078, T1195.002, etc.) es un objeto de este tipo.
campaign
Tipo de objeto STIX que representa una campaña de ataque. "SolarWinds Compromise" es una campaña con ID campaign--808d6b30-....
course-of-action
Tipo de objeto STIX que representa una mitigación. Ejemplo: M1032 Multi-factor Authentication. Las relaciones "mitigates" conectan estos objetos con técnicas.
relationship_type: "uses"
Relación STIX que dice "este objeto usó/empleó este otro". Aquí: campaign uses attack-pattern = "SolarWinds usó esta técnica".
relationship_type: "mitigates"
Relación STIX: course-of-action mitigates attack-pattern = "esta medida defensiva contrarresta esta técnica". Se cuentan estas relaciones para calcular el peso de cada nodo.
Kill chain
Secuencia de fases en un ataque, del reconocimiento al impacto. ATT&CK define 14 tácticas en orden. Las aristas del grafo siguen este orden.
Táctica
Un objetivo del atacante en el kill chain (ej: "initial-access"). Una técnica puede pertenecer a múltiples tácticas.
Sub-técnica
Variante específica de una técnica padre. T1558 = Steal or Forge Kerberos Tickets. T1558.003 = Kerberoasting (una forma específica).
CVE
Common Vulnerabilities and Exposures. ID único para una vulnerabilidad concreta. Ejemplo: CVE-2020-10148 = fallo en SolarWinds Orion que permitió el supply chain attack.
CVSS
Common Vulnerability Scoring System. Puntuación 0-10 de severidad. 9.0+ = crítico. Se convierte en peso: w = (10 - CVSS) / 10.
NVD
National Vulnerability Database (NIST). Base de datos oficial de CVEs con puntuaciones CVSS. Fuente de los datos de vulnerabilidad usados en este proyecto.
DiGraph
Grafo dirigido (Directed Graph). Las aristas tienen dirección: A → B ≠ B → A. Usado porque el atacante progresa en una dirección (del inicio al impacto).
Peso de arista w
Costo de recorrer esa arista. En este grafo = costo para el atacante de ejecutar la técnica destino. Menor peso = más fácil para el atacante = más peligroso.
Dijkstra
Algoritmo para encontrar el camino de menor costo desde un nodo origen a todos los demás. Aquí: de ATTACKER a IMPACT. Implementado desde cero con heap binario.
Floyd-Warshall
Algoritmo de programación dinámica que calcula distancias mínimas entre todos los pares de nodos. Factible aquí porque el grafo es pequeño (73 nodos = O(73³) = trivial).
FW-Betweenness
Métrica derivada de Floyd-Warshall: para cada nodo k, cuenta cuántos pares (i,j) tienen su ruta óptima pasando por k. Alto betweenness = nodo "puente" crítico.
SUNBURST
El malware inyectado en el proceso de compilación de SolarWinds Orion. Se distribuía en actualizaciones legítimas. Técnicamente: DLL trojanizada con comunicación C2 por HTTP.
APT29 / Cozy Bear
Grupo de amenaza persistente avanzada (APT) atribuido al SVR ruso (Servicio de Inteligencia Exterior). Principal actor detrás del ataque SolarWinds.
Supply chain attack
Ataque a la cadena de suministro: comprometer el proceso de producción/distribución de software para infectar a todos los usuarios finales que actualicen.
ATTACKER / IMPACT
Nodos conceptuales del grafo (no son técnicas ATT&CK). ATTACKER = punto de entrada externo (peso=0). IMPACT = objetivo final logrado (peso=0). Necesarios para definir inicio y fin de la ruta.
